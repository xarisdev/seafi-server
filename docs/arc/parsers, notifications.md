# Общее

> **Статус: базовый workflow реализован.** Ниже сначала приведены текущие ограничения/поведение, затем целевая архитектура. Реализация использует HTML выдачи Lalafo, PostgreSQL, фильтры, подписки и существующий WebSocket к Telegram-боту.

## Сбор Lalafo

Запросы выполняются через `httpx`; страницы разбираются `BeautifulSoup` с `lxml`. Источник данных — HTML-карточки `article[data-component="lf-ad-tile-horizontal"]`; Next.js `homeFeed` игнорируется, так как он содержит рекомендации, а не текущую выдачу. ID берётся из URL `/ads/...-id-<id>`, цена нормализуется в KGS, город — из URL объявления, дата публикации — из карточки в часовом поясе Кыргызстана (UTC+06:00). Owner берётся из профиля категории, а не из заголовка объявления.

Используются три URL-профиля:

1. `general-owner` — долгосрочная аренда от собственников по Кыргызстану.
2. `general-agency` — долгосрочная аренда агентств/риелторов по Кыргызстану.
3. `general-capital` — аренда квартир в Бишкеке; owner считается неизвестным (`any`).

Профили запускаются последовательно с паузой 90 секунд после каждого. За один проход каждого профиля загружается не более трёх страниц; между запросами страниц выдерживается пауза в одну секунду. Это ограничивает нагрузку, но также ограничивает глубину хранимой истории. При ошибке одного профиля остальные продолжают работу. Селекторы не зависят от хэшированных CSS-классов, но HTML сайта может измениться, поэтому parser нужно сверять с новыми fixtures при изменении Lalafo.

Повторная загрузка выполняется через `INSERT ... ON CONFLICT (ads_id, ads_source) DO UPDATE`; дубликаты не создаются. При повторном обнаружении профиль с известным типом владельца не перезаписывается общим профилем `any`.

## Сопоставление и подписка

Каждые пять минут объявления сопоставляются с фильтрами по городу, типу `rent`, owner и ценовым границам. Наличие фильтра означает желание получать уведомления; отдельно включать его не требуется. Создавать/настраивать фильтр можно до или после оплаты. Фильтр хранится при истечении подписки, но уведомления приостанавливаются.

Для delivery должны одновременно выполняться условия:

- объявление опубликовано после сохранённого baseline первого запуска;
- `published_at` не раньше начала подписки;
- у пользователя есть подписка с `expires_at > now`;
- поля объявления подходят под пользовательский фильтр.

Объявление без распознанной даты публикации сохраняется, но не отправляется, чтобы не создавать исторический backlog. Подписка проверяется повторно перед dispatch.

## Доставка

Уникальность `(ads_id, user_id)` не позволяет создавать повторную delivery-запись. Состояния: `pending`, `sending`, `sent`, `failed`. Бот получает через WebSocket событие с `delivery_id`, `telegram_id` и объявлением; после успешной отправки в Telegram он вызывает `POST /api/v1/deliveries/{delivery_id}/ack`. Неуспешная отправка возвращается в `pending` до пяти попыток. Нет ACK за три минуты — lease считается просроченным; восстановление выполняется в следующем пятиминутном цикле matching/delivery. Доставка имеет семантику at-least-once, поэтому бот должен дедуплицировать по `delivery_id`.

WebSocket-менеджер текущего сервера держит одну connection на процесс. Фоновые jobs защищены PostgreSQL advisory lock, чтобы не запускаться параллельно при нескольких API workers. Ошибки пишутся в лог; при настроенном `ADMIN_TELEGRAM_ID` критическая ошибка также передаётся боту событием `admin_alert`.

Примените миграции перед запуском: `alembic upgrade head`. Docker image выполняет это перед запуском Uvicorn.

## Модель объявления в коде

В `src/models/advertisement.py` определена ORM-модель со следующими полями:

```
Advertisement:
	id:           INT - PK       // Ключ
	ads_id:       TEXT           // Идентификатор объявления у источника
	ads_source:   INT            // EnumAdsSourceId: 1 (OPENL) или 2 (OPENH)
	url:          TEXT           // Ссылка на объявление
	title:        TEXT
	price:        INT | NULL
	city:         TEXT
	type:         TEXT           // rent | sell
	owner:        TEXT | NULL    // agent | owner | any; по умолчанию any
	created_at:   DATETIME       // Дата записи
	last_seen_at: DATETIME       // Дата последнего получения
	
	UNIQUE (ads_id, ads_source)  // constraint uq_id_source
```

`LALAFO` использует `ads_source=3`. Scraper обновляет `last_seen_at`; `published_at` хранит дату источника и может быть `null`, если её не удалось извлечь. Уникальность пары `(ads_id, ads_source)` задана ограничением модели.

`last_seen_at` предусмотрен для возможной будущей проверки актуальности; задача очистки объявлений не реализована.

## Модель доставки в коде

В `src/models/advertisement_delivery.py` описана ORM-модель учёта доставок:

Модель:

```
id:         PK
ads_id:     INT FK(Advertisement.id)
user_id:    INT FK(User.id)
status:     pending | sent | failed
attempts:   INT
sent_at:    DATETIME
created_at: DATETIME

	UNIQUE (ads_id, user_id)
```

В таблице модели поле `ads_id` является FK на `advertisements.id` (внутренний ID записи), `user_id` — FK на пользователя. Поля `attempts` и `sent_at` хранятся в модели; `sent_at` допускает `null`.

Уведомления отправляет Telegram-бот, а не сервер. Текущие endpoint и WebSocket payload описаны в [контракте Telegram API](../api/telegram-bot-contract.md).
