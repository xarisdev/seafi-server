# Общее

Ввиду особенностей парсинга я выбрал более общий подход к сбору информации чтобы не создавать большую нагрузку на сеть. Теперь планируется сбор объявлений в общую базу с последующей фильтрацией под запросы каждого пользователя. Разделим сбор на 3 подхода:

1. Общий-агентский — сбор всех объявлений у которых владельцем указаны: Агентство недвижимости или Риелтор.
2. Общий-личный — сбор всех объявлений у которых владельцем указан Собственник
3. Общий-столичный — сбор всех объявлений у которых городом указана местная столица (На данный момент — Бишкек)

Это заранее сконструированные 3 парсера, которые будут вызываться с интервалом в 90 секунд. Также у них планируется анти отказная система с уведомлениями для быстрого реагирования. О ней в другой раз.

## Структура

```
Parsers
 ↓

```

## Работа с полученными объявлениями

Результат каждого парсера сохраняется в базу данных. Модель следующего формата:

```
Advertisement:
	id:           INT - PK       // Ключ
	ads_id:       TEXT           // Идентификатор объявления у источника
	ads_source:   INT            // Идентификатор источника
	url:          TEXT           // Ссылка на объявление
	title:        TEXT
	price:        INT | NULL
	city:         TEXT
	type:         TEXT
	owner:        TEXT
	created_at:   DATETIME       // Дата записи
	last_seen_at: DATETIME       // Дата последнего получения
	
	UNIQUE (ads_id, ads_source)  // Уникальные пары
```

Проверять уникальность объявления призваны `ads_id` и `ads_source` . Если в разных источниках `id` объявления может повторятся, информация об источнике решит эту проблему.

Также, очень важен параметр `last_seen_at` , проверять актуальность объявления довольно таки сложно, но, если регулярно проверять записи и удалять объявления, которых не было видно последние скажем 1-2 недели, то база данных станет заметно легче. Шанс, что пользователю попадет неактуальное объявление крайне мал.

## Память отправленных объявлений

Мне кажется хорошим вариантом сделать отдельную таблицу.

Модель:

```
id:         PK
ads_id:     INT FK(Advertisement.id)
user_id:    INT FK(User.id)
status:     pending | sent | failed
attempts:   INT
sent_at:    DATETIME
created_at: DATETIME

UNIQUE (ads_id, user_id) // Уникальные пары
```

- Сервер отправляет пользователю новое объявление — статус “pending”.
- Клиент вернул успешную доставку — статус “sent”.
- При неудаче “failed” — планируем повторную отправку.

Пока для конкретного пользователя есть записи со статусом “failed” — пытаемся их обработать и перевести в “send”, но с ограничением в количества попыток — 5. Такой подход чтобы не плодить тысячи записей на одних сетевых неудачах.
