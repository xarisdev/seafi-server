## Очередь фильтров

Определимся с моделью фильтра:

```python
# Состояния работы с фильтром
class EnumFilterItemState(str, Enum):
    ACTIVE = "active"
    WAITING = "waiting"
    COOLING = "cooling"
    IN_PROGRESS = "in progress"
    DELETED = "deleted"

class InProgress(BaseModel):
    id: int
    taken_at: datetime
```

Теперь можно спроектировать очередь через asyncio. Шаблон без реализации (псевдо-класс):

```python
Queue:
	# Поведенческие параметры
	cooldown = 120.0
	lease_timeout = 60.0

	ready: asyncio.Queue[int] = asyncio.Queue()
	cooling: list[tuple[float, int]] = []
	in_progress: dict[int, InProgress] = {}
	active: set[int] = set()
			
	# Манипуляции
	async def activate: ...
	async def deactivate: ...
	async def get_waiting: ...
	async def put_back: ...
	
	# Синхронная обработка от агентов
	def _handle(message)
```

### Алгоритм:

1. Активация фильтра. - После того как фильтр был активирован, он помещается в `active` если его там не было.
2. Запуск фильтра. - Сразу после активации он помещается в `ready`
3. Когда приходит агент, он опрашивает `Queue` на предмет ожидающих фильтров.
4. Когда агент забирает фильтр, он удаляется из `ready` и помещается в `in_progress`
5. Когда агент завершает свою работу с фильтром, он возвращает его в очередь. Сам фильтр помещается в `cooling`.
6. `Queue` создает задачу вернуть этот фильтр в `ready` через `now()` + `cooldown` время.
7. Фильтр возвращается в `ready` и ждет пока его заберет свободный агент.

### Защита при удалении и ошибках

Если в очередь пришел запрос на удаление (деактивацию) фильтра. То очередь должна удалить его из своей памяти и вывезти из оборота. Если с первым проблем нет т.к. список в основном статичный, то со вторым может случиться ситуация, когда фильтр нужно удалить, а он уже в работе. Если он вернется в очередь и будет продолжать свое выполнение - мы за зря потратим ресурсы. Его результат все равно остановиться другими частями программы но лучше избегать такой методики.

## Агенты, менеджер

Поскольку агенты это скорее прокси между фильтрами, парсерами и вебсокетами, им необходим менеджер для правильной работы.

Есть 2 варианта реализации:

1. Агенты как сущности.
    1. Плюсы: Можно контролировать их количество, время работы, следовательно - эффективностью всего приложения.
    2. Минусы: Нужен отдельный менеджер для управления каждым агентом. Сложная логика распределения нагрузки.
2. Агенты как скрипты - **stateless**
    1. Плюсы: Нет сложной логики поведения агентов. Не нужен отдельный менеджер.
    2. Минусы: При росте нагрузки — кол-во агентов вырастет пропорционально и это может стать проблемой, ограничение по фильтрам не сможет распределить нагрузку.

## Контракт Итерации

```
Agent:
	IN: filter_id
	
	База данных: Получение Filter по его id
	
	Агент: Преобразование параметров Filter в конкретные инструкции, соответствующие специализации Агента
	
	Parser IN: Получение инструкций
	Parser: Выполнение инстуркций
	Parser OUT: Возврат результата инструкций
	
	База данных: Получение результата прошлых Итераций
	
	Агент: Сверка состояния БД с полученным результатом. (different)
	Агент: Подготовка формата результата (если он имеется, иначе - None)
		
	Результат: Отправляется напрямую в ParseResultHandler
	
	OUT: Возвращает filter_id в очередь
```
