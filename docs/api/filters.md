# Фильтры

Фильтр хранит предпочтения пользователя для поиска объявлений. В текущем сервере реализованы SQLAlchemy-модель и базовые API-операции создания, чтения и частичного обновления. Сам парсер, постановка фильтра в очередь и отправка объявлений этим API не управляются.

## Поля

| Поле | Тип | Значение по умолчанию | Описание |
| --- | --- | --- | --- |
| `id` | integer | генерируется БД | ID фильтра |
| `user_id` | integer | задаётся сервером | Внутренний ID пользователя; уникален, у пользователя может быть один фильтр |
| `city` | string | `"bishkek"` | Город; код не ограничивает список значений |
| `ads_type` | string enum | `"rent"` | Тип объявления: `rent` или `sell` |
| `ads_owner` | string enum или `null` | `"any"` | Тип владельца: `agent`, `owner` или `any` |
| `min_price` | integer или `null` | `null` | Нижняя граница цены |
| `max_price` | integer или `null` | `null` | Верхняя граница цены |

Для `min_price` и `max_price` схема API не задаёт ограничений вроде `>= 0`; валидируются только целые числа или `null`. Сервер также не проверяет, что `min_price` меньше `max_price`.

Пример ответа:

```json
{
  "id": 13,
  "user_id": 42,
  "city": "bishkek",
  "ads_type": "rent",
  "ads_owner": "any",
  "min_price": null,
  "max_price": null
}
```

## API

Базовый путь: `/api/v1`. Требуется заголовок `X-Api-Key`. Пользователя указывают одним из query-параметров `telegram_id` или `id`; если переданы оба, используется `id`.

### Создание

```http
POST /api/v1/filters?telegram_id=123456789
X-Api-Key: <X_API_KEY>
```

Тело не требуется: сервер получает пользователя и формирует `user_id` самостоятельно. Успех возвращает `200 OK` и объект `Filter`. Пользователь должен существовать.

### Получение по пользователю

```http
GET /api/v1/filters/user?telegram_id=123456789
X-Api-Key: <X_API_KEY>
```

Успех — `200 OK` и объект `Filter`. Если фильтр не найден, сервер возвращает `404`.

### Получение по ID фильтра

```http
GET /api/v1/filters/13
X-Api-Key: <X_API_KEY>
```

Успех — `200 OK` и объект `Filter`; неизвестный ID даёт `404`.

### Частичное изменение

```http
PATCH /api/v1/filters/13
X-Api-Key: <X_API_KEY>
Content-Type: application/json
```

Передаются только изменяемые поля. Пример:

```json
{
  "city": "osh",
  "ads_type": "rent",
  "ads_owner": "owner",
  "min_price": 10000,
  "max_price": 50000
}
```

Успех — `204 No Content`; фильтр с неизвестным ID даёт `404`. Допустимые значения `ads_type`: `rent`, `sell`; `ads_owner`: `agent`, `owner`, `any`, `null`.

## Ограничения текущей реализации

- Уникальное ограничение БД запрещает несколько фильтров на одного пользователя. Повторный `POST` не преобразуется маршрутом в специальный ответ и может завершиться ошибкой целостности БД.
- Endpoint удаления фильтра отсутствует.
- `POST /api/v1/filters/{id}/activate` и `/deactivate` скрыты из OpenAPI и являются заглушками: существующий фильтр приводит к `204`, но состояние не меняется. Не используйте эти методы как функциональность.
- Фильтры не добавляются в очередь обработки автоматически. В коде сервера не обнаружены `TaskManager`, `services.ads_handler` или реализованный pipeline парсинга и доставки объявлений. Проектное описание этого pipeline находится в [архитектурной заметке о парсерах и уведомлениях](../arc/parsers,%20notifications.md).
